Written 2026-10-26 for build step 1 (masterwork 15.2). Replaces `batch_c_probes.cu` of 2026-10-26 01:50, which never compiled (`CUBLAS_LT_MATMUL_DESC_TRANSA` is spelled `CUBLASLT_MATMUL_DESC_TRANSA`), unpacked the Q4_K scales wrongly, and measured a transposed GEMM under the name P-Q10 (P-Q10 is the fp8 probe). Definitions: trainer master 11.3 and ruling D35.

| Probe | What it measures | Rule |
|---|---|---|
| P-K1 | bf16 path: Q4_K weights dequantized to a bf16 scratch, then a tiled `mma.sync` GEMM (128x128x32 tile, cp.async two stages), on every real layer shape at M = 2048, 4096, 8192; efficiency against the P-H3 bf16 peak and against cuBLASLt on the same data; output checked against cuBLASLt | adopt the own kernel on a shape at >= 0.85x cuBLASLt; reopen the tile design if efficiency < 0.35 anywhere |
| P-K2 | int8 path: activations to int8 per row per 32, Q4_K quants unpacked to int8 in registers, `mma.sync` s8, per-sub-block fp32 epilogue; output checked against fp32 arithmetic on the same quantized inputs; cosine against the bf16 path | Mode F default only at >= 1.3x and KL no worse (P-Q6) |
| P-K3 | Q4_K and Q6_K streamed from VRAM and dequantized in registers (no mma), against a plain read of the same bytes in the same run | ALU-bound below 60 % of the plain read |
| P-Q10 | fp8 data gradient: cosine of dX = dY W with dY rounded to e4m3 or e5m2 per row, against fp32; gaussian and heavy-tailed dY | adopt only at cosine >= 0.999 and >= 1.3x (speed from the P-H3 peaks) |

Every sub-test refuses an allocation that would take the whole card above the 10.7 GiB ceiling (`--ceiling-gib`), and records NVML clocks, temperature, power and VRAM. The GGUF block layouts and dequantization formulas follow llama.cpp `ggml-common.h` / `ggml-quants.c` exactly; the probes check the GPU dequantizers against a host copy of those formulas. cuBLASLt is a test-only reference and is never shipped.

Files (added next to the Wave 0 probe sources; nothing existing is changed): `kernels_c.h`, `kernels_c.cu`, `probes_c.h`, `main_c.cpp`. The program also links the existing `kernels.obj` / `kernels.o` (plain read kernel) and `cpu_bw`.

Revision 3 (2026-10-26 14:4x): a redesigned int8 kernel (v3) runs next to v2 in P-K2, both checked against fp32 on the same quantized inputs. v2 reached only 0.18 to 0.28 of the int8 peak; the likely limit is its per-sub-block epilogue, whose int32 -> fp32 conversion (I2F) runs at a quarter of the fp32 rate on Ada. v3: exact magic-number conversion on the full-rate pipes (exact below 2^22; the largest sum is 32 x 127 x 15 = 60,960), the min term from scale x sum precomputed by the quantizer, the 4-bit words loaded once per K step for both sub-blocks, and ldmatrix.x4 for the A fragments. Revision 4 (2026-10-26 14:5x): revision 3 (v3) measured 0.96x to 1.03x of v2 on Windows, so the I2F conversion was not the limit. v4 keeps v3 and issues the 16 int8 products of a sub-block before any is scaled; v3 consumed each product right after its mma. v3 source kept as kernels_c.v3.cu in the backup.

Revision 5 (2026-10-26 14:5x): v4 also measured the same as v2 (0.96x to 0.99x). v5: registers capped for two blocks per SM (__launch_bounds__(256, 2)), weight scales prepared once per weight and streamed with the tiles (one barrier fewer per step). P-K2 now also reports registers, spill bytes, shared memory and blocks per SM for every GEMM kernel, so the next step is decided from facts.

Revision 6 (2026-10-26 15:0x): revision 5 measured the why: v2 and v4 use 216 and 223 registers per thread (one block per SM; bf16 uses 119, two blocks); v5 capped at 128 spilled 160 bytes per thread and ran 0.54x to 0.70x of v2. v6 keeps v5's arithmetic without the cap and uses smaller warp tiles (three variants), so the occupancy question is answered without spilling. P-K2 now times and checks every int8 version generically and reports all of them.

Revision 7 (2026-10-26 15:1x): revision 6 measured that occupancy is not the limit either (v6 at two blocks per SM without spills ran 0.68x to 0.97x of v2). The remaining cause, DERIVED from the P-H3 int8 peak (259.5 TOPS, 46 SMs, 2.775 GHz): each m16n8k32 product takes about 16 tensor cycles per sub-partition, while the per-32 fp32 epilogue issues about 20 instructions per product, so the tensor pipe waits on instruction issue. v7 quantizes activations with one scale per 256 (the Q4_K super-block; Q8_K-style layout written from scratch), applies the 6-bit weight sub-block scale in int32 (one integer multiply-add per accumulator per sub-block, exact: at most 8 x 63 x 60,960 = 30.7 M), applies d x activation scale once per super-block, and keeps one fp32 FMA per accumulator per sub-block for the min term. P-K2 times v7 with its own quantizer, checks it against fp32 on its own quantized inputs (reference generalized to an activation group size), and reports its cosine against the bf16 path next to the per-32 path's, so the precision cost of the coarser activation scale is measured, not assumed (KL in P-Q6).

Revision 8 (2026-10-26 15:2x): revision 7 measured v7 correct on all 20 shapes at 1.06x to 1.08x of v2 (252 registers, no spill), so the epilogue was about 7 % of the gap. DERIVED from that run: an int8 64-deep step holds about 1,024 tensor cycles per SM sub-partition against about 4,096 for the bf16 32-deep step, and the measured int8 step took about 3,440 cycles, so the two-stage pipeline at one block per SM does not hide the next load. v8 keeps v7's arithmetic and changes only the pipeline: 3 or 4 cp.async stages in dynamic shared memory (opt-in above 48 KiB), one barrier per step (v7: three), and a 16-byte weight record per weight row and super-block (d, eight 6-bit scales) prepared once per weight. New command `k2prof`: one launch of each GEMM kernel (bf16, v2, v7, v8) on one shape for Nsight Compute, so the stall reasons are measured instead of derived.

Revision 9 (2026-10-26 15:3x): revision 8 measured v8 (3 stages) at 1.17x to 1.21x of v2, 4 stages no better than v7. Nsight Compute on `k2prof` then MEASURED the why: tensor busy = 16 cycles per m16n8k32 / (instructions per mma x cycles between a warp's instructions / warps per scheduler); v2 24.7 x 4.6 / 2, v7 17.4 x 6.1 / 2, v8 16.8 x 5.6 / 2, predicting 28 / 30 / 34 % against 27.7 / 29.7 / 33.2 % measured. Every int8 version ran 2 warps per scheduler (216 to 252 registers, one block of 8 warps per SM). v9 keeps v8's arithmetic and puts 16 warps on the same 128x128 tile (512 threads, warp tile 32x32, registers capped at 128), with the weight scales laid out by column so each pair a thread needs is one load; 2 or 3 stages. Expected from the same equation if the other two factors hold (about 19 instructions per mma, 5.6 cycles): about 60 % tensor busy. `k2prof` profiles v9 too.

Revision 10 (2026-10-26 15:4x): Nsight Compute on revision 9 MEASURED that more warps raise each warp's wait (v9: 4 warps per scheduler, 19.0 instructions per mma, 9.35 cycles between a warp's instructions; 36 % predicted, 34.9 % measured), so the lever left is instructions per mma. v10 takes v8 (8 warps, 3-stage base) and removes the min term from the inner loop: per row and super-block, sum_j m_j * bsum_j is one bf16 m16n8k16 tensor-core product of exact digits (activation sums as 64 * hi + lo, weight mins as 64 * m and m; every value and product an integer below 2^24, checked on the host for every sum in [-4064, 4064]), applied once per super-block as acc -= sa256 * dmin * that. Inner loop per int8 mma: 1 mma + 4 IMAD (v8: plus 4 FFMA and 1.5 shared loads). 2 or 3 stages. `k2prof` profiles v10 too.

Revision 11 (2026-10-26 15:5x): revision 10 measured v10 (3 stages) correct at 1.02x to 1.14x of v8 (96.3 TOPS best, 1.50x to 2.00x bf16). Nsight Compute on v10: 13.4 instructions per int8 mma, 6.2 cycles between a warp's instructions, 2 warps per scheduler (39 % int8 tensor busy predicted, 37.7 % measured). v11 = v10's arithmetic with 16 warps per tile (512 threads, warp tile 32x32, registers capped at 128, load work spread over all warps), since v10 has a third fewer per-mma shared loads than v8, whose 16-warp version (v9) lost its gain to barrier and shared-queue waits. Also the open item of revision 10: the separate activation quantization at 32 MiB of bf16 input and up ran at 436 to 454 GB/s (about 90 % of the 504 GB/s published bandwidth; smaller inputs were L2-warm), so it is memory-bound, not a bug. P-K2 now times the conversions with a cold L2 (64 MiB overwritten before each call) and adds RMSNorm fused with the int8 quantization (the norm is the producer of every Q4_K GEMM input of a layer), comparing it with RMSNorm to bf16 and with the separate pass; the int8-over-bf16 ratio including norm and conversions is reported both ways.

Revision 12 (2026-10-26 16:0x): revision 11 measured v11 (v10 with 16 warps) at 0.88x to 0.95x of v10, so v10 3-stage stays the int8 kernel, and closed the M=8192 item (cold-L2: RMSNorm fused with the int8 quantization costs the same as RMSNorm to bf16; including norm and conversions the int8 path is 1.39x to 1.84x the bf16 path on all 20 shapes). New command `k2b` (P-K2b, kernel v12 = v10's arithmetic with split-K, grouped problems, a 64x128 tile and bf16 output): (A) split-K on the low-tile shapes, router and attn_k (32 or 64 tiles of 128x128 for 46 SMs at M = 2048 / 4096, about 70 % of the SMs busy, DERIVED), with expert down for comparison; (B) bf16 output against fp32 output on every shape (expert down writes 16 MiB of fp32 results against about 1.6 MiB of inputs at M = N = 2048); (C) MoE experts at M = 64 per expert (--expert-m), 256 experts (--experts): one grouped launch for all experts against one expert with split-K, and the bf16 kernel grouped the same way (synthetic equal routing); (D) layer order on one shared input, norm -> router -> q/k/v -> gate/up, each step timed inside the sequence and alone with a cold L2, for int8 and bf16 activations.

## Files and build

`kernels_c.cu`, `kernels_c.h`, `probes_c.h`, `main_c.cpp` and this file are Batch C. `cudautil.h`, `hostlib.h`, `nvml_dyn.h`, `kernels.h`, `kernels.cu` and `cpu_bw.cpp` are the Wave 0 probe framework (written 2026-10-22 to 10-23 for the same project), byte-identical to the copies the runs used. Results: `data/probe_results/batch_c/`.

Windows (Developer Command Prompt for Visual Studio, CUDA toolkit installed):

```
set PATH=%CUDA_PATH%\bin\x64;%PATH% && mkdir build && nvcc -std=c++20 -O2 -arch=sm_89 -c kernels.cu -o build\kernels.obj && cl /nologo /std:c++20 /O2 /EHsc /arch:AVX2 /c cpu_bw.cpp /Fobuild\cpu_bw.obj && nvcc -std=c++20 -O2 -arch=sm_89 -c kernels_c.cu -o build\kernels_c.obj && nvcc -std=c++20 -O2 -c main_c.cpp -o build\main_c.obj -Xcompiler "/EHsc /D_CRT_SECURE_NO_WARNINGS" && nvcc -arch=sm_89 build\main_c.obj build\kernels_c.obj build\kernels.obj build\cpu_bw.obj -lcublasLt -o build\pelias_batch_c.exe
```

WSL2 / Linux:

```
export PATH=/usr/local/cuda/bin:$PATH && mkdir -p build_wsl && nvcc -std=c++20 -O2 -arch=sm_89 -c kernels_c.cu -o build_wsl/kernels_c.o && nvcc -std=c++20 -O2 -arch=sm_89 -c kernels.cu -o build_wsl/kernels.o && g++ -std=c++20 -O3 -mavx2 -c cpu_bw.cpp -o build_wsl/cpu_bw.o && g++ -std=c++20 -O2 -I/usr/local/cuda/include -c main_c.cpp -o build_wsl/main_c.o && nvcc -arch=sm_89 build_wsl/main_c.o build_wsl/kernels_c.o build_wsl/kernels.o build_wsl/cpu_bw.o -lcublasLt -ldl -lpthread -o build_wsl/pelias_batch_c
export LD_LIBRARY_PATH=/usr/lib/wsl/lib:/usr/local/cuda/lib64:$LD_LIBRARY_PATH
```

Run: `pelias_batch_c all --out DIR` (k1, k2, k2b, k3, q10 with a 30 s cooldown), or one probe; `pelias_batch_c k2prof --out DIR` under `ncu --set full --kernel-name regex:k_gemm -o REPORT` for the stall profile.
