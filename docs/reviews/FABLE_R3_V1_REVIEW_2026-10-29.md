# R3 v1 review for v2 (read-only; nothing built, run or written)

Bytes per format in the token table (DERIVED from r3.cu lines 508-524 and the r3_formats.h block sizes): Q7_ZT 1,324 MB (0.941 B/value), Q4_TG2 330 MB (0.5625), Q5_K 202 MB (0.6875), Q6_K head 417 MB (0.820); sum 2,273 MB (matches the log's 2.272 GB). Warp tasks: 10 x 12,800 + 30 x 14,336 + 124,160 = 682,240 (DERIVED). Per SM share of 504 GB/s at an assumed ~2.5 GHz SM clock (not measured; v2 should print `clockRate`): 4.4 B/cycle, so one 3,584-B Q7_ZT task every ~810 cycles per SM, one 2,560-B Q4_TG2 task every ~580 cycles (DERIVED).

## 1. The four suspects

**(1) Only 2 blocks/SM because one kernel carries all four formats: partly.** The symptom is real (2 x 256 threads = 512 of 1,536 threads; nothing but registers can cause that, so the kernel is at 88-128 regs/thread, DERIVED from 65,536 / (3 x 256) = 85 → the 3-block cap is 80). The mechanism is not "four formats": the branches are mutually exclusive, so the count is the max live set, which is the Q7_ZT branch alone: `xw[32]` + `wd[29]` (lines 74, 85) + ~16 regs of Job pointers (8 pointer fields, 2 regs each, lines 46-54) + temporaries. A per-format kernel would land in the same bracket. What actually buys occupancy: drop `xw[32]` (32 regs; see item 5 below), collapse the 8 pointers to 2 bases with fixed offsets, store log2(lpr). Whether occupancy matters at all is untested: by Little's law 16 warps x 3.5 KB x ~50 % load-phase duty ≈ 28 KB in flight per SM (DERIVED), enough on paper for 504 GB/s at ~1 us latency; the read ceiling kernel needed its best (blocks/SM, unroll) pair to hit 494 and that pair is only in the PC log (D:/pelias-tests/gp/TD/ceil_20261029_021046.log), not in BUILD_LOG.md. Read it: it says how many 16-B loads per SM the memory system wanted.

**(2) Binary search + Job field loads before every weight load: right, second-order.** 11 dependent probes per task (log2 1,091), each `jobs[mid].task0` in a 104-B struct on its own line; the table is 113 KB (DERIVED), too big to stay in L1 next to the streaming lines, so the lower levels are L2 hits (~300 cycles). Per warp: 927 tasks x 11 probes x ~170 cycles average ≈ 1.7 M cycles ≈ 0.7 ms of the 8.79 ms (~8 %, DERIVED with assumed hit latencies), during which that warp has nothing in flight; plus ~14 scalar field loads and two runtime integer divisions (`lane / J.lpr`, `lane % J.lpr`, line 231: ~40-60 instructions per task, about 10 % of a Q7_ZT task's ~400). Also every consecutive task of a warp in the expert region is in a different job (stride 736 > 256 tasks per job), so no reuse. Worth killing, but it does not explain 259 vs 494.

**(3) Q4_TG2 grid in __constant__ with divergent addresses: right, and the headline.** `c_grid[(tb >> 2g) & 3][code]` (line 144-147) compiles to an LDC with a per-lane address; the constant cache serves one distinct address per pass. Every lane in a warp sits in a different (row, block, half), so tags and codes are independent across lanes: with the probe's random bytes, 64 x (1 - (63/64)^32) = 25 distinct addresses per LDC (DERIVED). 128 LDC per lane-task x ~25 passes ≈ 3,200 constant-pipe cycles per warp task vs the 580-cycle memory budget: Q4_TG2 tasks are ~5x compute-bound. Total: 143,360 tasks / 46 SMs x 3,200 ≈ 10 M cycles ≈ 4.0 ms (DERIVED, assumes one address per cycle and ~2.5 GHz). And because the table is job-ordered, all 736 warps are in Q4_TG2 at the same time (16 jobs x 256 tasks = 5.6 rounds per layer), so nothing memory-bound overlaps it. Decomposition if this holds: 330 MB in ~3.6-4.0 ms (~85 GB/s) and the other 1.94 GB in 4.8-5.2 ms (375-405 GB/s). Real weights have peaked code and tag distributions (maybe 8-15 distinct per LDC), so v1 overstates Q4_TG2's cost vs the real file, but it stays several times over budget.

**(4) Stage boundaries drain the pipe: right, and the sync itself is unmeasured.** Stage bytes (DERIVED, DeltaNet layer): 23.7 / 7.9 / 10.2 / 6.0 MB = 48 / 16 / 21 / 12 us at 494 GB/s, so 23.6 us per boundary is one to two whole stages. Expected pieces: drain ≤ 1 task cycle (~1-2 us), ramp ~ loaded latency (~1 us), cg grid.sync on 92 blocks (unmeasured; typically a few us), restart burst (736 warps x 11 search probes + 14 field loads through L2 at once). That adds to ~5-11 us, so ~half of 23.6 is unaccounted: measure the sync alone (161 syncs, no tasks). The fix you named is the right one: weights do not depend on the sync, so a warp should issue its first next-stage weight loads *before* waiting, then wait, then load activations. Expected boundary cost → about the barrier latency alone.

## 2. Other limits found in the code

- **Q6_K and Q5_K do ~6 instructions per value in scalar integer math** (lines 183-186, 208-216: 3 to extract q, 1 BFE for x, IMAD, add). Head: 124,160 tasks x ~870 warp-instr = 2.35 M per SM ≈ 0.6 M issue cycles ideal (0.24 ms) vs 0.84 ms of DRAM time for the head at 494 (DERIVED): hidden only if issue efficiency stays above ~30 % while most warps stall on memory. Both formats pack naturally into dp4a: Q6_K low nibbles `word & 0x0F0F0F0F`, high bits `((qh_word >> s) & 0x03030303) << 4`, OR, dp4a with `xw[8p + l/4]`; the `-32` folds out as `-32 * xsum[jg]` (exact in integers, `xsum` already exists). Q5_K the same with `& 0x01010101`. About 1.5 instructions per value instead of 6 (DERIVED).
- **Q4_TG2 does an I2F per value** (`static_cast<float>(sx8(...))`, line 147): 4,096 conversions per warp task at 16/clk/SM = 256 cycles per task on the conversion pipe; per SM 0.8 M cycles ≈ 0.32 ms vs 0.67 ms of Q4_TG2 DRAM time (DERIVED). Second to the LDC, but it is on the same tasks.
- **Activation slice in registers:** `xw[32]` is the biggest fixed register cost and is reloaded (8 x LDG.128, L1 hits) for every task although it is identical for every task of the same job and part.
- **Job-ordered table phase-locks the formats:** at any moment all warps run the same format, so a compute-bound format cannot hide under a memory-bound one. Fine once every format is memory-bound; worth remembering when reading per-format numbers.
- **Gated-H branch in Q7_ZT** (line 111): per-lane divergent, 2 of 8 blocks gated, so the warp executes the 32-instruction hx block for every jj with ~25 % of lanes active (~128 mostly-masked instructions per task). Branchless with H = 0 costs the same; the popcount route from tdecode is the real alternative. Q7_ZT is memory-bound with ~4x margin (DERIVED: 1,407 M values x ~3.5 instr / 32 lanes = 154 M warp-instr, 0.33 ms ideal vs 2.68 ms DRAM), so low priority.
- **`asm volatile` on the loads: not a limiter.** It only stops NVVM deleting, hoisting or merging them; ptxas still schedules the resulting `ld.global.cs`. The activation `__ldg`s and the weight loads are all in flight together.
- **memcpy-to-byte arrays (Q5_K/Q6_K):** with full unrolling they become BFE/PRMT on registers; the log's "no local memory" was the clang PTX check, not nvcc. One `cudaFuncGetAttributes` print (numRegs, localSizeBytes) settles it for the PC build.
- **Shuffle reduction, y writes, lane split for K = 512, grid tail:** all fine. y traffic ~7 MB per token (DERIVED, 0.3 %); (b)'s last round has 704 of 736 warps busy (DERIVED); the per-row headers both lanes of a block load (Q4_TG2 16 B, Q5_K 48 B) are same-address within one instruction, coalesced, no extra DRAM sectors.
- **Launch-size ceiling is gone in (b), so v3's "no gain" verdict does not carry over.** gemv_w3's two-rows-in-flight pipelining was tested when the per-launch ramp was the bound (BUILD_LOG 02:11); in a persistent kernel it is a live option again.

## 3. Ranked v2 changes

1. **Measure per-format first (no kernel change).** Four extra (b) rows, each a table of one format at ≥ 256 MiB (Q7_ZT dense only, Q4_TG2 only, Q5_K only, Q6_K head only). Prediction (DERIVED, from the LDC estimate): Q4_TG2 ~80-120 GB/s, Q7_ZT ≥ 430, Q5_K / Q6_K 350-450. This decides the weight of everything below in one run.

2. **Q4_TG2 grid: replicated shared-memory LUT.** 32 copies of the 64 floats, lane L reads `lut[L + 32 * (tag * 16 + code)]`, bank = L, conflict-free, 8 KB per block, exact (same floats as `c_grid`). Why: removes the ~25-way LDC serialization; 128 LDS per lane-task at 1 wavefront each ≈ 0.4 M cycles per SM for the whole token (DERIVED). Expected: (b) from 8.79 ms to ~6.1 ms (~375 GB/s) if the decomposition in suspect 3 holds; (c) stage-2 time of each layer drops the same way. Test: Q4_TG2-only (b) before/after. Add the magic-number int-to-float (`__int_as_float(((v ^ 0x80) & 0xff) | 0x4B000000) - 8388736.f`, exact for int8, 2 full-rate ops instead of one 16/clk I2F) in the same branch as a second step. Longer-term, format-changing option: define the grids as int8 levels / 127 (grids 0 and 3 are already exact integers (i - 7) with scale /8; grids 1 and 2 would round) and go dp4a; that needs a requant + KL run, so not for v2.

3. **Q5_K and Q6_K: dp4a packs** as in section 2. Why: ~4x fewer instructions on 619 MB of the token, takes the head from "probably hidden" to memory-bound with margin. Expected: Q6_K-only (b) up to ~0.1-0.3 ms faster on the head if it is currently issue-limited; zero if not (the per-format row tells you). Test: Q6_K-only and Q5_K-only (b) before/after; `r3 check` stays the gate.

4. **Job lookup: one load instead of eleven.** Every job's ntask is a multiple of 256 (256 / 2,048 / 4,096 / 124,160; DERIVED from line 427 and the shapes), so a `uint16 job_of_chunk[t >> 8]` of 2,665 entries (5.3 KB, L1-resident) replaces the search; pad any future job to 256-task boundaries. Plus a compact 32-B Job (one weight base with fixed offsets for hdr/mask/hb/d6, one activation base for xq/xs/xsum, y offset, fmt | log2 lpr | n packed) so the field fetch is 2 x 16-B loads, and shifts/masks instead of `/` and `%`. Expected: 5-10 % on (b) (DERIVED from the ~8 % search estimate + the division cost), and a smaller restart burst per boundary in (c). Test: (b) with the chunk index alone, then with the compact Job.

5. **Bytes in flight.** Step a: `__launch_bounds__(256, 3)` and `(256, 4)` as a compile switch, print numRegs / spills; if no spills, read (b). Step b: move the activation slice to shared memory, transposed per lpr (`act_T[word][part]`, conflict-free for lpr = 4/16/32) and hand out tasks block-major in chunks of 8 (one chunk per block iteration, so all 8 warps are in the same job and the block stages the activation once per job change with one `__syncthreads`); frees 32 regs per lane and the per-task xw reloads. Step c: two tasks per warp in flight (v3's RPL = 2 on the weight registers only, 56 regs) if the regs allow 3 blocks/SM. Expected: unknown, 0-30 % on (b); the ceiling log's blocks/SM column is the prior. Test one step at a time against the Q7_ZT-only row.

6. **(c): load-before-wait, and a per-stage counter instead of cg grid.sync.** Each warp: issue the weight loads of its first stage-(s+1) task, then fence + `atomicAdd(done[s])`, spin until `done[s] == tasks_in_stage[s]`, then load activations and compute. Why: the drain and ramp vanish (DRAM demand never stops), and the wait is per warp, not per block. Expected: per boundary from 23.6 us to about the barrier latency (a few us; measure). Over 160 boundaries (c) - (b) from 3.78 ms toward ~0.5-1 ms (DERIVED, assuming 3-6 us per barrier). Tests, in order: (c0) 161 syncs with empty stages = pure sync cost; (c1) counter barrier, empty stages; (c2) load-before-wait on the full table. `prefetch.global.L2` of the rest of the next stage by warps that ran out of tasks adds little beyond this: 736 warps x 3.5 KB already puts ~2.6 MB of the next stage in flight, and the idle tail is too short to pull 24 MB (DERIVED); `cp.async.bulk.prefetch` is sm_90+, not sm_89.

7. **Real-token sync count.** The four all-to-all points per layer are real (norm → qkv; core → o; o → residual/norm/router → gate/up; down → next layer), and the GEMV side cannot start early (every output row needs the whole vector), so the overlap is weight-side only. What can go: (i) gate/up → down as a per-expert counter (512 tasks per expert), down warps load weights, then wait on their expert's counter, the last gate/up warp of the expert does silu(g) x u and the int8-per-32 quant for that expert: -40 grid barriers; (ii) router → experts hidden behind the shared expert's gate/up (independent of the router, 2 MB per layer); (iii) RMSNorm's reduction needs no barrier of its own: per-32 int8 codes are scale-invariant, so quantize x g in the same pass and multiply y by 1/rms after the GEMV; (iv) the DeltaNet state read (126 MB per token per the game plan) is prefetchable before the stage-0 barrier like a weight. v2 can emulate (i) with the present table and fixed activations.

8. **Small: drop the 161st `grid.sync()`** after the head (line 253); `(tc - tb) / 160` already assumes 160.

Stacked expectation for (b) (DERIVED, assumption-laden): 259 → ~375 after item 2 → ~400-420 after 3-4 → the Q7_ZT-only row tells whether item 5 is needed to reach the 445-494 band.

## 4. Harness notes

- **Cold flush leaves ~36 MB dirty in L2** (64 MiB memset, line 563): the timed kernel pays those write-backs (+1.6 % traffic, DERIVED) and a dirty-eviction ramp. Same in `tdecode ceil`, so ratios to the ceiling are fair and absolutes are ~1-2 % pessimistic. Keep it for comparability, or flush by reading 64 MiB and re-run the ceiling the same way.
- **Random Q4_TG2 bytes are the worst case** for the LDC divergence (25 of 32 distinct addresses); a real expert tensor would show fewer. After item 2 the cost is data-independent, so the probe becomes fair again; until then, label v1's Q4_TG2 share "random-data worst case".
- **(a) may be host-bound under WSL2.** 1,091 queued launches at 19.1 us each (DERIVED, 20.81 ms / 1,091); if host submission is slower than the GPU consumes, (a) measures the driver, not today's kernels. Replay the same 1,091 launches from a CUDA graph for the GPU-only baseline. Its grid `min(ceil(tasks/8), 368)` (line 583) also puts a 256-task job on 32 SMs with one task per warp, which mimics gemv_w's whole-matrix-in-flight shape, so it is a fair "today" model but an upper bound.
- **Shared dy scratch:** harmless (0.3 % of bytes); concurrent same-line writes from many SMs merge in L2. It does hide one real-token cost: the y → next-stage activation path (quant per 32 + scales) does not exist in the probe; item 7 adds it.
- **Print what settles the suspects:** `cudaFuncGetAttributes` numRegs / localSizeBytes for both kernels, `clockRate`, occupancy per variant, and the new rows (per-format (b), empty-stage (c)). The occupancy figure alone cannot distinguish 88 from 128 regs.
- **Timing method is sound:** warm-up, memset on the same stream before e0, median of 7, cooperative grid = nsm x occ (co-resident). Only the 7-rep median is thinner than the ceiling's 50; (b) and (c) are long enough that it does not matter.

# Addendum: the 552 GB/s peak, the power cap, and WSL2

**Peak and ceilings (DERIVED from the coordinator's nvidia-smi figures).** Memory at 11,501 MHz vs 10,501 stock → peak 552 GB/s. Token floor at the card's peak: 2.272 GB / 552 = 4.12 ms; at the measured 494 asymptote 4.60 ms; v1 (b) 8.79 ms = 47 % of the card, (c) 12.57 ms = 33 %. The read-only kernel's 494 is 89.5 % of the card; achievable DRAM efficiency on GDDR6X is typically ~90-93 %, so of the 58 GB/s gap only ~10-20 GB/s is plausibly recoverable by more bytes in flight, the rest is DRAM protocol overhead (refresh, page switches). Consequence for the ranking: item 5 (bytes in flight) gains a little weight (the ceiling kernel itself may have been slightly under-subscribed, which the ceiling log's blocks/SM x unroll sweep will show), but the order stays: Q4_TG2 LDC (item 2) and the per-task costs (items 3-4) are still where the 2x sits. The per-SM budget tightens by 9.5 %: 12.0 GB/s per SM, ~4.8 B/cycle at the assumed 2.5 GHz, so a Q7_ZT task every ~745 cycles and a Q4_TG2 task every ~530 (vs ~3,200 cycles of LDC serialization in v1: the 5x compute-bound figure becomes ~6x).

**Power cap (200 W of 216, 198 s of SW power capping logged).** A memory overclock plus a kernel that streams at the card's peak is exactly the case that draws the cap, and capping lowers the SM clock, not the memory clock. That lengthens only the compute-bound phases (v1's Q4_TG2 LDC serialization, the Q6_K head's ~6 instr/value), and leaves DRAM-bound phases alone. So it is one more reason items 2-3 come first: once every format is memory-bound, clock capping stops costing bytes. Two things to add to v2's run sheet (Windows side, not something I can see from here): log `nvidia-smi dmon -s pc` (SM clock, memory clock, power, throttle reasons) across the `r3 stream` run, and print `clockRate` from the probe; a (b) rate that moves with the SM clock marks a compute-bound phase, one that does not marks a memory-bound one. Until the clock during the run is known, every "cycles → ms" number in my report carries that assumption.

**WSL2 GPU-PV, HAGS off.** This affects host-to-GPU submission, not device-side synchronization:
- The empty launch's 3.07 us (BUILD_LOG 02:11) was measured inside WSL2 already, so the per-launch ceiling table and the derived 7.8-8.1 ms per-token read time (02:2x) include the WSL cost; native would be somewhat lower. Mode (a)'s 19.1 us per queued launch (DERIVED) is therefore even more likely host-submission-bound under GPU-PV with HAGS off (every submission goes through the kernel-mode scheduler on the Windows side); the CUDA-graph replay of (a) is the only way to get the GPU-only baseline, and the native-vs-WSL difference is a separate, unmeasured number (a Windows-native build of the probe would give it).
- cg `grid.sync()` and the per-stage counters in item 6 are device-side (atomics and spins on an L2 line); the GPU-PV path is not in that loop, so the 23.6 us per boundary is not a WSL artefact and the empty-stage (c0) measurement stands as the way to split it. The one WSL cost in (c) is the single cooperative launch per token (once, not per boundary).
- Design consequence, in R3's favour: with submission expensive and HAGS off, one persistent launch per token (or per several tokens) removes the host from the per-token path almost entirely; the real engine should also keep its non-GEMV stages inside that launch rather than as separate kernels (item 7), since each extra kernel costs a GPU-PV submission.

Ranking after both corrections: unchanged in order (1 measure per format, 2 Q4_TG2 shared LUT, 3 Q5_K/Q6_K dp4a, 4 job lookup, 5 bytes in flight, 6 load-before-wait + counter barrier, 7 real-token sync cuts, 8 trivial); item 5's expected ceiling moves from "445-494" to "494-~510", and items 2-3 gain the power-cap argument. Harness additions: dmon log during the run, `clockRate` print, CUDA-graph replay of (a), and a note in the log that every R3 number is WSL2 + overclocked memory at 552 GB/s peak (the 504 figure in the game plan's floors should be re-derived: 193 tok/s at 100 % of 504 becomes ~211 at 552, DERIVED as 193 x 552/504).
