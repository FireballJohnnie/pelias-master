## The report, word for word

**Overall verdict**

The masterwork is a serious, well-labelled specification and most of its numbers trace cleanly to the trainer/engine ledgers (I re-derived the byte map, the quant block table, the DRAM/PCIe/drive link arithmetic, the Section 21 factors, and cross-checked the two profiles against the CSV: all consistent). It is close to ready for steps 1–3 (probes, foundations, quantizers). Before the build is queued, four things should change: (1) the VRAM ceiling must say which reading the governor enforces (process-only vs whole-card), because the trainer master already ruled on this and the profiles silently use the other basis; (2) the zero-copy third-branch gate copied from the blueprint is provably unreachable on the reference machine and must be restated; (3) the Windows 10, Vulkan and local-API-security items are presented as settled design where they are either infeasible as written or unresolved dependencies; (4) a handful of numbers are mislabelled or inconsistent (46.4 GB/s, 1.49 s, "44 to 54 tok/s", 62.9 MiB). None of these invalidates the design; they are precision and feasibility fixes.

**Findings**

1. **MAJOR — The ceiling is defined two ways and the document does not carry the existing ruling.** `docs/PELIAS_SYSTEM_MASTERWORK.md` 0.3 rule 3, 4.3, 7.6, 18.1 C9; both reference profiles' `plan_basis`. The governor rule (D28) measures the *process* budget (CUDA free after context − margin = 10.7 GiB), but every "peak" the profiles compare against is a *whole-card* reading that includes ≈0.9–1.0 GiB held by Windows (RESULTS §2: "GPU memory in use is for the whole card including the desktop"; §9.4 "idle 551 MiB"). The trainer master already settled this: `PELIAS_TRAINER_CUDA_MASTER_SCAFFOLD.md` line 2127: "decision 7; ruled 2026-10-24 for the probe-measured, process-only ceiling, with the whole-card figures kept as the stricter planning figures until P-E4 re-measures", and gives the process-only headroom as ≈1.0–1.3 GiB (8-bit core "would fit at both micro-batches"). The masterwork's 7.6 instead invents a weaker reason for a higher ceiling ("the engine's own allocator turns out leaner"). Consequence: on the first real run the recommender of 7.6 will fire immediately on the reference machine (≈1 GiB more room than `plan_basis`), which is correct but unexplained, and the C9 sentence "its peak 10.67 to 10.69 GiB is under 10.7 on the whole-card reading" compares two different quantities. Fix: state decision 7 in 4.3 and 7.6; add `basis: "whole_card" | "process"` to `plan_basis` in both JSON profiles and the CSV; make P-E4 (record NVML-used before start and at peak) part of step 10's gate.

2. **MAJOR — The E12 zero-copy gate cannot pass on the reference machine.** Masterwork 10.4: "the gate holds (GPU at least 15 GB/s and combined at least 1.25 times the CPU alone)", copied from the blueprint line 135. `pelias-engine/benchmarks/RESULTS.md` §1 already records this test as failed-by-physics: "The test's own greenlight asks for the combined rate to reach 1.25x the CPU alone (57.4 GB/s). It reached 1.04x … dual-channel DDR4-3200 peaks at 51.2 GB/s, so 57.4 GB/s cannot be reached on this machine". As written, `gpu.cold_zerocopy_branch: auto_probe` (both profiles) can never switch on. The real reason to want the branch is not bandwidth but CPU compute: E0 measured 10.1 ms of CPU cold compute against 2.86 ms modelled (WAVE0 3.4 finding 1), so moving a share to the GPU frees CPU time even at zero bandwidth gain. Fix: gate on measured decode tok/s with the branch on vs off (3 launches per side) and "combined ≥ 1.0× CPU alone, GPU share ≥ 15 GB/s", and say so in 10.4 and the profile provenance.

3. **MAJOR — Windows 10 is accepted (A2, 13.4) without the driver constraint that may make it infeasible.** 13.2 requires a driver "new enough for the program's CUDA runtime" and the Windows build uses nvcc 13.4.92 with the static runtime (B2). To my knowledge NVIDIA's R580 branch (CUDA 13.0 baseline) is the last branch announced for Windows 10; later branches may never ship for it. A binary linked against the 13.4 static runtime may therefore demand a driver a Windows 10 machine cannot get. I am not certain of the exact cut-off; it needs verification before N7. Fix: record it as UNVERIFIED with the check (NVIDIA's Windows 10 support notice and the minimum driver of the 13.4 toolkit); if confirmed, either build the Windows installer with the 13.0 toolkit (the WSL one) or restrict the product to the 13.0 API surface under CUDA minor-version compatibility and ship SASS for every listed arch (no PTX JIT on the older driver). Also 13.4's "sm_75, sm_86, sm_89, sm_120 plus PTX" misses sm_80/sm_90; PTX from sm_89 cannot JIT on an 8.0 card, so state which PTX is embedded.

4. **MAJOR — The Vulkan backend (3.1, 4.3, step 13) has an unstated third-party build dependency and an unmeasured platform gap.** Vulkan compute needs SPIR-V binaries; producing them needs glslang/shaderc/DXC (LunarG/Khronos tools, not "the platform's own tools" of 13.3) or an own SPIR-V emitter, which is not in the tree (14.2 has no shader compiler). On WSL2 there is no vendor Vulkan path for NVIDIA (only the experimental Mesa-on-D3D12 route), so both the Vulkan backend and ReBAR route A are Windows-native/Linux-native only; 10.6 says "unmeasured" for WSL2 but 4.3 does not. The backend is also a second full kernel set (GEMM, attention, DeltaNet, quantizers, backward) scheduled in one step with AVX-512, the dense plug-in and more quant formats. Fix: decide the SPIR-V route as an explicit DECISION (proposed) with its licence entry in THIRD_PARTY_NOTICES.md; split step 13 into 13a (dense plug-in, AVX paths) and 13b (Vulkan), and mark 13b as after the first benchmark.

5. **MAJOR — The local web server has no stated defence against cross-site requests or SSRF.** 11.1/11.2 expose `/api/*` (start probe, quantize, train, import files by path, start the FlareSolverr process) and `/v1/chat/completions` on 127.0.0.1:8062 with no Origin/Host check or CSRF token; any web page the user visits can POST to it, and the model's `web.fetch` tool can be steered by a fetched page to request 127.0.0.1:8191, 8062 or LAN addresses. Fix (12.2 Guards, 11.2): reject requests whose `Host` is not the bound address, require an `Origin`-checked session token for `/api/*`, block private and loopback ranges in `web.fetch` unless USER-FORCED, and add this to PG12.

6. **MAJOR — Serving and training on the same 12 GB card is not arbitrated.** 11.6 says long jobs "run in a worker process started by the server, so a training run never stalls the API", but the server holds a 7.5 GiB bank + KV (whole-card 10.7 GiB) while training needs 7.90–9.00 GiB (8.8), and on WSL2 the two pinned stores (18.65 + 28–33 GiB) exceed the 48 GB cap together. Fix: one GPU owner at a time — `pelias serve` unloads (or refuses to start a job) and the governor checks free VRAM and pinned RAM across processes before a worker starts.

7. **MAJOR — Order of operations puts the author's stated goal last.** The first benchmark (16.4, A13) is step 16, after the Vulkan backend, web tools and installers (13–15). F0–F2 and the speed test need only steps 1–11. Fix: move the benchmark to right after step 11 (quality F0/F1/F2/F5, speed) and repeat it at release; keep P-E15 (which needs Vulkan/D3D12 interop code) with the ReBAR path at step 15, leaving only the BIOS on/off pair in step 1.

8. **MINOR — "46.4 GB/s" Windows host read is labelled MEASURED but is not in the records.** 4.2, 17.2 ("44.8 to 46.4"). WAVE0 3.3 and MACHINE_AND_DRIFT line 55 give Windows best 4-thread read as 44.8; the 46.4 appears only in the author's input `pelias-universal-build-master.md` line 94, whose provenance REVIEW.md does not vouch for. Fix: check the raw Windows P-H2 JSON; otherwise print 44.8 or label 46.4 UNVERIFIED.

9. **MINOR — 1.49 s does not follow from 35.8 GiB.** 8.2 item 3: "79 fetches, about 35.8 GiB per step, 1.49 s at 26.1 GB/s" and the token thresholds 1,495/2,242/2,989. 35.8 GiB = 38.44 GB ÷ 26.1 = 1.47 s; 1.49 s is 2 × 18.164 GiB (80 fetches), the trainer master's own mixed usage (lines 107/1832 vs 821). Fix: 1.47 s and 1,473 / 2,210 / 2,947 tokens, or say the threshold is computed on the 80-fetch bound.

10. **MINOR — "WSL2 44 to 54 tok/s short" (10.7, 21.2, 21.4) contradicts 17.4 and WAVE0.** WSL2 Cell A measured 37.9 short / 42.1 at 12 k (WAVE0 3.4 table row 1; masterwork 17.4 lists it). Fix: "37.9 to 55.7 short, 42.1 to 53.4 at 12 k over all cells" or name the cell.

11. **MINOR — Unlabelled or source-less numbers.** 11.2 "62.9 MiB" snapshots (only in the input docs; DERIVED: 30 layers × 32 × 128 × 128 × 4 B + conv state ≈ 62.8 MiB — give the formula); 17 "491 numbers" (not in MASTER.md); 8.8 "600 / 1,200 / 2,000" fine as DECISION but the "643 to 2,031" prediction should name the GEMM-efficiency range (trainer table 1816: f = 0.75, 1,000–2,000 tok/s rows); the long master's sha256 is given as `c935a4a4…` (line 12) while every engine spec file cites `56634f43` for the 2026-10-24 build — say which version.

12. **MINOR — Stall gate threshold changed without a reason.** 16.1 rung 5 "stall ≤ 5 % at ≥ 3,072 tokens per step"; trainer T10 and P-T7 say "≥ 16 k tokens". Fix: cite the trainer's 16 k or justify 3,072.

13. **MINOR — Kernel tolerances: "slightly tighter" is wrong by three orders and the references differ.** 16.2 says the trainer's 6.11 is "slightly tighter (1e-6 and 1e-4)" than 1e-3/2e-3. Trainer 6.11 measures bf16 GEMM at rel. L2 ≤ 1e-6 against an fp64 GEMM of the *same bf16-rounded inputs* (accumulation order only); the universal spec's 1e-3 is against a different reference. Fix: state the reference for each tolerance; keep 6.11's definitions verbatim.

14. **MINOR — Reference threads do not match the engine's threading model.** Profiles `cpu.threads 6` (READ-SRC, llama.cpp `-t 6`) while 10.5 says cold workers are "one per physical core … never sharing a core with the decode thread" (7 on the 5800X3D) and 4.2 defaults to `physical − 1`. Fix: label 6 as "llama.cpp-measured; E-A1 re-measures on the Pelias engine", and make `vram.ceiling_mode: probe_auto` vs `vram.ceiling_override_gib: 10.7` precedence explicit (7.2 does not say which wins).

15. **MINOR — Privacy: drive-layout paths and the persona name in tracked files.** `profiles/reference_pelias/qwen36_35b_a3b_q4km_model_profile.json` lines 142–145 (`<drive path>\…`); masterwork 15.1, 15.2 step 1, 19.2, Section 20 (`<drive path>`, three of them). These pass `verify_inventory.py` because its scan only matches `C:\Users\` and `/home/x`. They reveal the author's directory layout and the assistant's persona name, which rule 7 keeps out of repository files. Fix: replace the profile's drive paths with the engine-repo copies (`pelias-engine/benchmarks/raw/stage2-tier-cuda/hot-sets/`, which exist for b7.0–b8.5); move drive paths in 15/19/20 to the local-only profile or write them by role; extend the scanner with `[A-Z]:\\` outside `docs/inputs/`.

16. **MINOR — Which GGUF is "the reference model" is ambiguous.** 5.2 and the model profile describe the served 753-tensor file (the author's v0.2 fine-tune export, "test-model" in RESULTS) and attach hot sets, hit rates and the float spread to it; 16.4 F1/F2 and P-X6 compare Stage A against the *clean baseline* made from the Unsloth bf16 re-upload (trainer 529, 1458). The hot set and float spread transfer to the clean base only as an assumption. Fix: name both files and their keys in 5.2; add "re-profile the hot set on the clean base" to step 10.

17. **MINOR — CPU-only mode and dense inference are stated as if they exist.** 3.1 says the cold-expert AVX kernels "run the whole model"; the tree has `cpu/` expert kernels only, no CPU spine (attention, DeltaNet, norms). 5.4 offers streamed dense inference with no bound; the DERIVED bound is cold bytes ÷ 47.6 GB/s (≈1 s/token for a 40 GB dense file). Fix: mark CPU-only as a later step and show the dense bound on the plan card.

18. **MINOR — Licence notices.** The quantizers and type rules are "re-expressed" from ggml source (5.3, 8.6 step 3); a bit-identical re-expression is at least arguably a derivative of MIT code, so THIRD_PARTY_NOTICES.md should carry the llama.cpp/ggml MIT notice even though no file is copied; add the Unicode data licence (B6). FlareSolverr MIT is fine as a separate process.

19. **NIT** — H1–H5 in 4.7 are called "R1 to R5" in 3.1 and "R2, R3" in 4.3 (collides with requirements R1–R33); PG numbers are renumbered against `PROPRIETARY_RUNTIME_SPEC.md` (its PG3 is the tokenizer, PG9 speed) without saying so; 8.2 "flushed once per batch" vs D27/P-H12 "a flush after each enqueue"; 21.2 "Before: every byte crosses PCIe" is not the stock baseline (stock computes cold experts on the CPU); 21.3 "64 GiB … 5.3× the card's 12 GB" mixes GiB and GB; 14.3 omits `server → web` and `server → flow` though `/api/*` and tool calls need them, and `tok → none` implies a second JSON parser; P-D2 should name `tojson` formatting parity (Python `json.dumps` spacing/escaping) as a known trap; 8.4 should confirm the author's builder *rejects* rows over 4,096 rather than truncating them; Section 21.3 (13 fields) could move to a separate hypotheses file to keep the spec tight.

- The quant block table (5.3), the byte map (17.3), the DRAM/drive/PCIe derivations (4.4, 4.5) and the Section 21.2 factors: all arithmetic checks out.
- Profiles: JSON settings and CSV agree key-for-key (119/119), every setting has a provenance row, `local_only/` is git-ignored and untracked, no e-mail, token or account name in any tracked file.
